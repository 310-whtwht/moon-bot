# 戦略ラボ（戦略を検証する仕組み）

売買戦略を、開発のテストや CI と同じように検証する仕組みです。
人や AI の注意力に頼らず、これまでの失敗を仕組みで止めることを目的にしています。

このラボが行うのは、ボットのバックテストを実行して読むことだけです。Paper・本番・データベースの設定は変えません。
「合格」は Paper の候補になったという意味で、Paper や本番に進めるかは人が決めます。

## 開発のハーネスとの対応

| 開発 | このラボ | 場所 |
|---|---|---|
| 要件の一覧 | 注文の流れの台帳。誰が、なぜ売買せざるを得ないかの一覧です | `flows.yaml` |
| 仕様書 | 仮説カード。実行の前に、理由と値を書いて固定します | `hypotheses/` |
| テスト・CI | 9つの検査。1つでも落ちたら不合格です | `gates.py` |
| git の履歴 | 試行台帳。すべての試行を残します | `ledger.csv` |
| レビューの記録 | 判定の結果 | `verdicts/` |
| マージの権限 | カードの `stage` を変えられるのは人だけです | カードの `stage` |
| テストのテスト | 検査の試験と、答えのわかっている戦略での校正 | `test_gates.py`、H-0001・H-0002 |

## 使い方

1. 注文の流れの一覧を見ます。案はチャートからではなく、ここから作ります。

   ```bash
   uv run research/lab/lab.py flows
   ```

2. 使える相手が無ければ、`flows.yaml` に足します。誰が、なぜ値を選ばずに売買するのかを書いてください。書けない案は作りません。
3. 流れの id を指定して、新しいカードを作ります。今のデータで確かめられない流れ（`testable: blocked`）は止まります。

   ```bash
   uv run research/lab/lab.py new H-0011-short-name F-005
   ```

4. `hypotheses/H-0011-short-name.yaml` を書きます。`why`（誰がなぜ注文を出すか）と `counterparty`（誰の損が自分の利益になるか）が空だと実行できません。
5. 戦略のスクリプトを `strategies/research/` に置き、カードの `script` に場所を書きます。
6. 検査を実行します。Docker で1つずつ順に動かすので、銘柄と `neighbors` の数によって数分かかります。

   ```bash
   uv run research/lab/lab.py run H-0011-short-name.yaml
   ```

7. 全体の状況を見ます。

   ```bash
   uv run research/lab/lab.py status
   ```

検査そのものの試験は、次のコマンドで実行します。

```bash
uv run research/lab/test_gates.py
```

## 9つの検査

| 検査 | 基準 | 止めたいこと |
|---|---|---|
| 回数 | 30回以上 | 少ない取引での判断 |
| 偶然でないか | t 値が、試した数に応じた値以上 | たくさん試して当たりを拾うこと |
| 利益の厚み | PF 1.3 以上 | コストや環境の変化で消える薄い利益 |
| 前半と後半 | どちらも PF 1 超 | 一時期だけの偶然 |
| 最近の3分の1 | PF 1 超 | すでに消えた効果 |
| 大勝ち頼みでないか | 大きい3回を除いて PF 1.1 以上 | 数回の大勝ちに頼った成績 |
| コストへの強さ | 滑り3倍で PF 1.1 以上 | 本番の約定で消える利益 |
| 値を少しずらす | 3分の2以上が PF 1 超、中央 PF 1.1 以上 | 特定の値だけの当てはめ |
| でたらめな売買に勝つか | p 0.01 以下 | 相場全体の動きを実力と見間違えること |

基準を変えるのは、結果を見る前に、人の判断で行ってください。候補に合わせて緩めないでください。

## これまでの失敗と、止める仕組み

| 起きたこと | 止める仕組み |
|---|---|
| COT の判定の効果を、取引を後から消して計算し、過大に報告した | 成績は必ずボットのバックテストの取引から計算する |
| 月末フィキシングを手書きの計算で t 3.4 と評価した（ボットでは t 2.06） | 同上 |
| 結果を見て値を選び、その成績を実力と見間違えた | 実行後にカードやスクリプトを変えると止まる。revision を上げると、新しい試行として数える |
| 40通り以上試して、当たりを拾った | 台帳が試した数を数え、必要な t 値が上がる |
| 生成 AI の提案の数字を、そのまま信じそうになった | カードの数字ではなく、実行した結果だけで判定する |
| 説明できない案を候補に残した | `why` と `counterparty` が空だと実行できない |
| 決済を 6:55 にして、スプレッドの拡大で負けた | 入りか決済のスプレッドが普段の3倍を超えると注意を出す |
| 拡大は6〜7時だけと思い込み、7時台に入る案を作った（実際は 6:00〜8:30） | 同上。時刻を決め打ちしない |
| チャートや公開指標から案を作り、合格がなかった | カードは `flows.yaml` の相手に紐づかないと実行できない |
| 検証用のデータが一時フォルダから消えた | 足のデータは `research/lab/.cache/` に置く（git には入れない） |

## 守ること

- 進める順は `idea` → `paper` → `live` です。`stage` を変えるのは人だけで、AI は変えません。
- 台帳（`ledger.csv`）は追記だけにします。不合格の行も消さないでください。消すと、試した数を正しく数えられません。
- 同じデータを見て思いついた案は `found_on_same_data: true` にします。合格しても、まだ見ていない期間（Paper）で確かめるまでは証拠になりません。
- `why` に書いても、理由が正しいとは限りません。空でないことしか確かめていないので、内容は人が読んでください。
- 検査の前提の `PRIOR_TRIALS`（100）は、ラボの前に手で試した数の概算です。数えた値ではありません。

## 配当の日程を足した結果（2026-11-03）

F-006 を、配当の日程で確かめられるようにしました。日程は次のとおりで、値は実行前に固定しました。

- 期末配当: 3月期決算会社の株主総会の集中日（東証の公表値。2024/6/27、2025/6/27、2026/6/26）の翌平日から10平日。支払いは総会の翌日から始まる会社が多い
- 中間配当: 12月の最初の平日から10平日。支払日は会社ごとで、12月上旬で近似した
- 投資信託の決算は、分配金を円で払うので向きが円買いになりうること、25日はゴトー日と重なり分けられないことから、検査に含めていない

| H-0011 配当の支払い時期の買い（ボット、10:30〜15:00） | 不合格。60回 PF 0.95、t -0.14。EUR/JPY PF 0.9、GBP/JPY PF 1.03 |

Paper の版と同じ値で検査しました（トレンドライン 1.0.0、ドンチャン 1.2.0）。どちらも結果を見て選んだ戦略なので、`found_on_same_data: true` です。

| カード | 結果 | 勝率 | 1回あたり（100通貨） | 3年の損益 | 最大DD |

- トレンドラインは9つの検査のうち7つに通りました。落ちたのは「偶然でないか」（t 1.59、必要 3.07）と「利益の厚み」（PF 1.29、必要 1.3）です。ほかの銘柄ではすべて負けました（GBP/JPY PF 0.87、EUR/JPY 0.85、AUD/JPY 0.9）
- ドンチャンは3年で6回しか取引がなく、このラボでは判定できません。値を少しずらすと PF が 0.62〜4.19 と大きく変わります。スワップも計算していません。長い期間の検証は [2026-10-30-donchian-portfolio.md](../../docs/backtests/2026-10-30-donchian-portfolio.md)（FRED の日足、Python）にあります

## まだ無いもの

- Paper の実績とバックテストのずれを見る検査。今のラボの判定は、過去データまでです。
- FRED の日足を使う Python の検証（`research/longterm/` など）。ボットのスクリプトにした戦略だけが対象です。
- スワップ。ボットのバックテストが計算しないので、長く持つ戦略は実際より悪く出ます。
